# 基本設計 Skill

要件定義書を入力に、機能分割・画面・API・テーブル・権限を設計し基本設計書を作成する。
**設計判断は必ず `docs/architecture.md`（方式設計書＝SSoT）に準拠する。**

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | `docs/projects/{案件名}/requirements.md`（前工程 `/requirements` の成果物） |
| 参照 | `docs/architecture.md`、サンプル実装（`backend/web-sample` の `message`・`auth`、`frontend/src/features/messages`） |
| 出力 | `docs/projects/{案件名}/basic-design.md`（テンプレート: `templates/basic-design-template.md`） |
| 次工程 | `/detail-design` が機能単位でこの成果物を入力とする。完成後 `/review-design` でレビューする |

## 進め方

1. 要件定義書を読み、未確定事項が設計に影響しないか確認する（影響する場合はユーザーへ確認）
2. **機能分割**: ユースケースを、独立して実装・テストできる単位（＝機能。おおむね1リソースの CRUD または1業務操作）にまとめる。機能 ID（`{案件略号}-{連番3桁}` 例: `ORDER-001`）を採番する
3. **画面設計**: 画面一覧・画面遷移・各画面の主な項目と操作。サンプル（一覧＋モーダルでの登録・更新）の型で足りるかを先に検討する
4. **API 設計**: API 一覧（メソッド・パス・operationId・認可ロール）。規約は `docs/architecture.md` §3.2
5. **テーブル設計**: `app` スキーマのテーブル・カラム・制約（一意・外部キー）・インデックス
6. **権限設計**: ロール × 機能（参照・登録・更新・削除）の表

## 設計判断で必ず記載すること

- 機能分割の**理由**（なぜこの単位か。結論だけ書かない）
- 業務ルールの実現場所（API 定義の制約 / ドメインの不変条件 / DB 制約 / 画面の入力チェック）
- 一覧のページング・並び順・検索条件
- 同時更新・重複登録の扱い（一意制約と 409 応答など）
- web-core・frontend core の部品で足りない処理があれば、その旨と基盤拡張の提案

## 禁止事項

- `docs/architecture.md` に反する設計（必要なら先に方式設計書の改訂を提案する）
- 命名規約（architecture.md §10）・API 規約（§3.2）に従わない名前
- 根拠のない設計判断（要件定義書の記述・件数規模を根拠として示すこと）
