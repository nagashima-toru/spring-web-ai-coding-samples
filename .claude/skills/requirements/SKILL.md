# 要件定義 Skill

Web アプリの要件をヒアリング・整理し、後続の基本設計の入力となる要件定義書を作成する。

## 入力と出力（工程連鎖）

| | 内容 |
|---|---|
| 入力 | ユーザーへのヒアリング内容、既存資料（現行画面・業務フロー・帳票・データ仕様など） |
| 出力 | `docs/projects/{案件名}/requirements.md`（テンプレート: `templates/requirements-template.md`） |
| 次工程 | `/basic-design` がこの成果物を入力とする |

案件名はユーザーに確認し、英小文字ケバブケース（例: `order-management`）とする。

## 進め方

1. **既存資料の確認**: 提示された資料を読み、判明している事実と不明点を分離する
2. **ヒアリング**: 以下の観点で不明点を質問する（一度に3〜5問まで。まとめて聞きすぎない）
3. **要件定義書の作成**: テンプレートに落とし込み、不明点は「未確定」と明記して残す
4. **確認**: ユーザーへ要約を提示し、認識齟齬がないか確認する

## ヒアリング観点

### 業務要件
- 誰が（利用者の種類・ロール）、何のために（背景・目的）、どの業務で使うか
- 扱うデータ（項目・桁・必須・一意性・件数規模）と、その発生元・利用先
- 利用者の操作の流れ（ユースケース）。一覧・検索・登録・更新・削除・承認など
- 入力チェック・業務ルール（重複禁止・状態遷移・計算式）
- 権限（ロールごとに見られる・操作できる範囲）

### 画面・操作
- 必要な画面と画面遷移、1画面に出す項目
- 一覧の検索条件・並び順・ページング・件数
- 多言語対応・アクセシビリティ・対応ブラウザ／端末

### 非機能・運用要件
- 同時利用者数・応答時間の目標・データ量（現在と将来）
- 監査（誰がいつ何をしたかの記録）の要否、データの保持期間
- セキュリティ（個人情報の有無・マスキング・認証方式の制約）
- 外部システム連携（API・ファイル）の有無

## 判断の指針

- 画面レイアウト・API の形・テーブル構成はこの工程では決めない（基本設計の責務）
- ただし設計に影響する事実（ロール・件数規模・業務ルール・連携先）は必ず確定させる
- 「未確定」が残ったまま次工程へ進む場合は、要件定義書の未確定一覧に理由と確認先・解決時期を書く
