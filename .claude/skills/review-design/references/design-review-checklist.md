# 設計レビュー チェックリスト

## 共通

- [ ] 前工程の成果物（要件定義書・基本設計書）と矛盾がなく、要件の漏れ・要件にない機能の追加がない
- [ ] 未確定事項が明記され、設計判断に影響しない理由・前提が書かれている
- [ ] ステータス・版・変更履歴が更新されている

## 基本設計

- [ ] 機能分割の理由が書かれ、機能 ID が採番されている（architecture.md §10）
- [ ] 画面一覧・遷移・API 一覧・テーブル一覧・権限表がそろっている
- [ ] API のパス・メソッド・operationId が規約どおり（architecture.md §3.2）
- [ ] 全 API に認可ロールが決まっている。公開 API（認証不要）は理由がある（§4）
- [ ] テーブルは `app` スキーマ、snake_case 複数形、主キー・一意制約・インデックスが妥当（§7）
- [ ] 一覧のページング・並び順（一意に決まるか）が決まっている
- [ ] 業務ルールの実現場所（API 制約 / ドメイン / DB / 画面）が決まっている
- [ ] 個人情報の扱い（表示・ログ・マスキング）が決まっている

## 詳細設計

- [ ] openapi.yaml の追加分が、型・必須・制約・応答ステータスまで確定している
- [ ] エラー応答の type が architecture.md §5.2 の表から選ばれている
- [ ] クラス構成がレイヤ規約（§2.1）に従い、使う web-core 部品がクラス名まで特定されている
- [ ] 基盤部品にある機能（認証・エラー応答・ページング・API クライアント）を独自実装する設計になっていない
- [ ] トランザクション境界がユースケースにある（§6）
- [ ] 重複登録・同時更新の扱い（一意制約違反 → 409）が設計されている
- [ ] SQL がスキーマ修飾・バインド変数・ページング・一意な並び順になっている（§7.2）
- [ ] 画面の入力チェックが API の制約と一致している
- [ ] 表示文言が文言キーで管理され、`data-testid` が決まっている
- [ ] ロールによる表示制御と API の認可が一致している（表示制御だけに頼っていない）
- [ ] エラー事象ごとに例外・HTTP・画面表示が決まっている
- [ ] 単体・結合・E2E のテスト観点が列挙されている
