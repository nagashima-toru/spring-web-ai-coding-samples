# 一気通貫パイプライン Skill

`docs/projects/{案件名}/requirements.md` が確定している状態から、PR 作成までの全工程を
既存 Skill（`basic-design` 〜 `e2e-test`）に委譲しながら自動的に進める。

**この Skill 自身は設計判断をしない。** 各工程の実体は `.claude/skills/{skill}/SKILL.md` であり、
本 Skill の役割は「どの工程を・誰に（どのモデルのサブエージェントに）・どの順で・どこまで自動で流すか」の制御に限る。

## 対象範囲

- **入力**: `docs/projects/{案件名}/requirements.md`（ステータスが「確定」であること）
- **スコープ外**: `/requirements`（ヒアリングは対話が必須）。設計判断に影響する未確定事項が残っていれば開始しない
  （解決時期が後続工程と明記されたものは対象外とし、該当工程のサブエージェントに確定させる）
- **出力**: 基本設計書〜E2E 実施記録一式、実装コード、PR

## 実行方針（モデル・実行主体）

| 工程 | 実行主体 | モデル | 理由 |
|---|---|---|---|
| 基本設計・詳細設計 | サブエージェント | 上位モデル（Opus） | 機能分割・API/画面設計に推論が必要 |
| 設計レビュー・コードレビュー | サブエージェント | 上位モデル（Opus） | レビューは必ずサブエージェント＋上位モデルで行う |
| 実装・単体テスト・結合テスト・E2E テスト | サブエージェント | 作業系モデル（Sonnet） | 設計書どおりに作る作業系タスク |
| PR 作成（コミット・プッシュ・PR） | **主エージェント本人** | — | 他者に見える・取り消しにくい操作のため委譲しない |

サブエージェントは `subagent_type: general-purpose` とし、モデルは `model` パラメータで明示する。
作業系サブエージェントが早期エスカレーション条件（`docs/development-guide.md` §5.3）に達したら、上位モデルへ1回だけ昇格して再試行する（昇格後は最大2ラウンド）。

## 進め方

1. **事前確認（すべて満たすまで次に進まない）**:
   - requirements.md が存在し、ステータスが「確定」で、設計判断に影響する未確定事項がない
   - `git status` がクリーン（無関係な変更があれば停止して確認する）
   - `main` から feature ブランチを切る（`main` 上で設計書・コードを生成しない）
   - `docker info` が成功する（結合テスト・E2E の前提）
   - `git rev-parse HEAD` で起点コミットを控える
2. 以下を**順番に**実行する（並列化しない。後続が前工程の成果物に依存し、機能間でテーブル・API の整合を取るため）
3. 各工程のサブエージェントへのプロンプトには必ず次を含める:
   - 対象の `.claude/skills/{skill}/SKILL.md`（と参照する `templates/`・`references/`）を読んで従うこと
   - 入力ファイルの絶対パス
   - その工程の検証ループを実際に実行し、成功するまで（上限内で）繰り返すこと
   - **ユーザーに質問できない**こと。確認が必要な箇所は §「委譲先 Skill の記述を上書きする点」に従い報告に含めること
   - 完了時に ①成果物パス ②検証結果（コマンドと結果） ③レビュー工程は区分別件数と対応 ④未確定・要確認事項（`[Ask]` を含む） ⑤設計書を改訂した場合はその内容 を返すこと
4. **基本設計→レビュー**: `basic-design` → `review-design`（[Must]/[Should] はサブエージェントが自己修正）。`[Ask]` が残れば主エージェントがユーザーに確認する
5. **詳細設計→レビュー（機能ごと）**: 基本設計書の機能一覧の各機能 ID について 4 と同様に行う
6. **実装〜結合テスト（機能ごと）**: `implementation` → `unit-test` → `integration-test`。プロンプトに「詳細設計書は手順5でレビュー済み」と明記する
7. **コードレビュー**: 実装した機能全体に `review-code`（指摘を全て自己修正し、検証まで通す）
8. **E2E テスト**: `e2e-test` でシナリオ作成・実装・実施・記録まで行う
9. **最終検証**: 主エージェント自身が backend `./mvnw clean verify` と frontend のチェック（`docs/development-guide.md` §1.4）を通す
10. **PR 作成**: 主エージェントがコミット・プッシュ・PR 作成を行う
    - コミット対象は起点コミット以降に**パイプラインが生成・変更したファイルのみ**（`git add -A` で無関係な変更を巻き込まない）
    - 本文は実装 PR 用テンプレートの見出しに沿い、設計 PR 用テンプレートのセルフチェックと設計レビューの実施記録も含める
    - 本 Skill の起動を PR 作成の承認とみなす
11. 実行した全工程・各工程の検証結果・PR リンクを簡潔に報告する

## レビュー指摘の扱い

- `review-design` / `review-code` のサブエージェントは **[Must]・[Should] を必ずその場で修正**し、修正後に検証を通してから報告する
- **[Ask]** は修正せず持ち帰らせ、主エージェントが `AskUserQuestion` でユーザーに確認してから反映する

## 委譲先 Skill の記述を上書きする点

| 委譲先 Skill の記述 | パイプライン実行時の扱い |
|---|---|
| `review-design` 手順4「ユーザーの了承を得て反映」 | [Must]/[Should] は了承なしで自己修正し報告する。[Ask] のみ返す |
| `review-code` 手順4「修正はユーザー了承後」 | 同上（修正後に検証まで通す） |
| `unit-test` 手順3「テストケース表をユーザーに提示」 | 提示先を主エージェントとし、完了報告に含めたうえで実装まで進める |
| `e2e-test` 手順1「シナリオ一覧をユーザーと合意」 | 同様に完了報告に含めたうえで、実施・記録まで進める |
| `implementation` 手順1「未レビューならユーザーへ確認」 | 手順5でレビュー済みであることを主エージェントがプロンプトで保証する |
| `basic-design` 手順1「未確定事項が影響する場合はユーザーへ確認」 | 影響ありと判断したら止め、確認事項として主エージェントへ返す |

## 停止して確認するタイミング

既定は「確認なしで最後まで進める」。ただし次は必ず止めて、主エージェントが `AskUserQuestion` でユーザーに確認する。

- 事前確認（手順1）が満たせない
- 設計工程で新たな未確定・矛盾が見つかった、または `[Ask]` が残った
- 検証ループが昇格後も解消しない
- E2E のシナリオがローカルで実施できない
- 破壊的操作が必要になった（既存データの削除、適用済み Flyway ファイルの変更が必要と判明した等）

## 禁止事項

- 事前確認の省略、`main` 上での作業
- 工程の入れ替え・レビュー工程の省略
- [Must]/[Should] の「対応不要」判断を独断で行うこと
- 検証を弱めること（`docs/development-guide.md` §5.4）
- PR 作成をサブエージェントへ委譲すること、パイプラインの成果物以外をコミットに含めること
