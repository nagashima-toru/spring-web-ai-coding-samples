## 決定済み
- 節の位置と見出し：§3 の末尾（§3 の箇条書き「設計と実装を1つの PR にする場合…」の後、`## 4. ` の直前）に、見出し行 `### 3.1 依存更新 PR（Dependabot）` で足す。§3 の既存の本文・表は変えない。表の「上記以外（プロセス・ドキュメント・設定・依存更新）」の行はそのまま残し、新しい節から「依存更新 PR のテンプレートは上の表の『上記以外』の行に従う」と参照する形にする
- 節に書く内容と、そのまま書く語（受け入れ基準2〜4がこの語を探す）：
  - 仕組み：`.github/workflows/dependabot-review.yml` が `dependabot[bot]` の PR を契機に AI（claude-code-action）で影響を確認し、結果を PR にコメントして `ai-review:safe` か `ai-review:needs-human` のラベルを付ける
  - 自動マージの条件：Dependabot の PR であること・更新種別が `version-update:semver-patch` か `version-update:semver-minor`・AI の判定が safe、の3条件をすべて満たす時だけ、AI とは別のジョブ（`automerge`）が `gh pr merge --auto --squash` で auto-merge を有効化する。マージの可否は AI ではなくワークフローの条件が判定し、AI にはマージを許可していない。auto-merge は有効化するだけで、必須チェックが通った時点で GitHub が squash でマージする
  - major の扱い：`version-update:semver-major` は AI の判定に関係なく `ai-review:needs-human` になり、影響分析のコメントだけが付く。マージは人が行う
  - CI 失敗時の扱い：「CI が失敗した」PR は必須チェックが通らないため auto-merge が有効でもマージされない。原因の確認と修正は人が行う（AI はコードを変更・push しない）。フェーズ3 のワークフロー（CI 失敗時の原因分析コメント）はまだ無いので、その仕組みは書かない
  - 利用枠：Pro プランの利用枠は人の対話利用と共有で、上限に達すると AI のステップが失敗し、判定は `needs-human` として扱われ auto-merge に進まない
- 人が行う設定は、次の順の番号付きリストで書く（順序が要件）：
  1. シークレット登録：ローカルで `claude setup-token` を実行して発行したトークンを、`CLAUDE_CODE_OAUTH_TOKEN` という名前で Actions secrets と Dependabot secrets の両方に登録する（Dependabot が起動したワークフローからは Dependabot secrets しか読めないため）
  2. ブランチ保護：main のブランチ保護で必須チェック `backend`・`frontend`・`e2e`（`.github/workflows/ci.yml` のジョブ）を設定する
  3. auto-merge の許可：リポジトリの Settings > General の「Allow auto-merge」を有効にする。必須チェックが設定されていないまま auto-merge を有効にすると即時マージされうるので、必ず2のブランチ保護を先に設定する（「即時マージ」の語を書く）
- 「ブランチ保護」の語は、人が行う設定の2より前（節の前半）に書いてもよいが、「Allow auto-merge」の語は3より前に書かない（受け入れ基準4が最初の出現の順を見る）
- 認証の記述は `CLAUDE_CODE_OAUTH_TOKEN` だけにし、`ANTHROPIC_API_KEY`・`anthropic_api_key` は書かない（API キーは使わない決定のため）。受け入れ基準5の検索範囲から `vault/` を除くのは、`vault/designs/` の設計文書が「API キーは使わない」という決定の記録として語を含み（フェーズ3 で削除される）、`vault/plans/`・`vault/tasks/` も計画の記述として語を含むため
- ブランチ保護・auto-merge の許可・シークレット登録は人がリポジトリ設定で行い、ワークフローや API から設定しない、と書く
- 補足として、`GITHUB_TOKEN` で有効化した auto-merge によるマージでは、main への push を契機とするワークフロー（CI の `push` 起動）は動かない（GitHub の仕様で `GITHUB_TOKEN` による操作は新しいワークフローを起動しない）ことを1文で書く。基準では確かめない
